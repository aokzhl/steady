# Гайд по навыкам Matt Pocock для Steady

Навыки Matt Pocock — инструкции для AI-агента на отдельных этапах разработки. Ты выбираешь задачу и нужный режим работы; агент читает соответствующий `SKILL.md` и следует ему. Установка добавляет эти инструкции в проект. Дальше работу запускает твой запрос, а подходящие вспомогательные навыки агент может применять по ходу задачи.

Для начала достаточно помнить `$ask-matt`, `$to-spec`, `$to-tickets` и `$implement`. Остальные навыки нужны в конкретных ситуациях.

## Как запускать навыки

В нашем Codex-чате используется знак `$`, например `$ask-matt`. В исходных инструкциях автора часто написано `/ask-matt`: это название того же навыка в интерфейсах с другим синтаксисом вызова.

После названия можно написать задачу обычными словами:

> $ask-matt Мы обсудили MVP Steady. Я хочу сначала оформить требования, затем реализовывать по одной задаче. Какой следующий шаг?

Или указать нужный навык напрямую:

> $implement Реализуй задачу из GitHub Issue с указанным номером.

Большинство навыков, управляющих процессом — `to-spec`, `to-tickets`, `implement`, `implement-spec`, `grill-with-docs` — настроены на явный вызов пользователем. Вспомогательные навыки, например `tdd`, `codebase-design` и `code-review`, агент может использовать автоматически, когда текущая задача им соответствует. Основной навык также может прямо поручить агенту вызвать вспомогательный.

Твои ограничения в запросе сохраняют приоритет. Например, «сейчас только документ, без кода» ограничивает работу документацией. Для простого объяснения SwiftUI достаточно обычного сообщения; каждый разговор не обязан проходить полный процесс разработки.

## Что меняется в работе

| Ситуация | Что делает навык | Что получаешь |
| --- | --- | --- |
| Идея ещё не определена | `grill-with-docs` уточняет поведение и фиксирует термины и решения | Меньше догадок при реализации |
| Требования уже обсуждены | `to-spec` собирает их в спецификацию | Явные границы работы и критерии проверки |
| Работа большая | `to-tickets` предлагает небольшие законченные задачи и зависимости | Возможность проверять результат по частям |
| Пора писать код | `implement` ведёт реализацию через проверки и ревью | Законченное изменение и коммит |
| Нужно проверить сделанное | `code-review` отдельно смотрит соответствие требованиям и стандартам | Две независимые оценки изменения |
| Процесс прошёл плохо | `retro` предлагает улучшения инструментов, проверок и инструкций | Более удобная среда для следующей задачи |

Взамен появится больше явных договорённостей: агент может уточнять поведение, предлагать разбиение работы и согласовывать границы тестов. Это полезно для неоднозначных функций. Для маленькой понятной задачи можно сразу перейти к реализации.

## Короткий маршрут для нашего MVP

### Настройка проекта

`setup-matt-pocock-skills` сообщает остальным навыкам, где хранить задачи, какими метками пользоваться и где читать документацию проекта.

Для Steady выбран GitHub `aokzhl/steady`, репозиторий подключён как `origin`. Настройка завершена: выбран `AGENTS.md`, стандартные метки созданы, правила трекера и чтения документов находятся в `docs/agents/`.

### Затем зафиксировать MVP

Мы уже обсудили основное поведение, поэтому новое полное интервью не требуется. Следующий результат — спецификация текущего MVP:

- Нативный клиент на SwiftUI с панелью AppKit у моноброви.
- Свободный локальный таймер, профили и задачи.
- Изменение оставшегося времени на значение от −20 до +20 минут.
- FastAPI для задач, профилей, результатов и статистики.
- Результат сначала сохраняется на Mac, затем отправляется серверу с защитой от дублей.
- Активный таймер между устройствами в MVP не синхронизируется.
- Неотправленные результаты переживают перезапуск приложения.

Если нужен только файл `docs/MVP.md`, попроси создать именно его обычным сообщением. `$to-spec` используй, когда хочешь спецификацию в трекере: его стандартный результат — публикация в GitHub Issues после завершения настройки. Он также проверяет с тобой, на каких публичных границах будем тестировать поведение.

Пример для публикации:

> $to-spec Собери согласованные требования MVP Steady. Таймер работает локально, сервер получает результаты. Полную синхронизацию и веб-клиент оставь за пределами MVP.

### Разбить работу на проверяемые задачи

`$to-tickets` сначала показывает разбиение и зависимости. После согласования публикует отдельные задачи в настроенном трекере.

Пример:

> $to-tickets Разбей спецификацию MVP на небольшие задачи, результат каждой из которых можно проверить отдельно.

Хороший пример задачи для Steady: «Завершённая сессия сохраняется на Mac и доставляется в FastAPI без дублей». В ней есть наблюдаемое поведение целиком: окончание фокуса, локальная запись, HTTP-запрос и серверное сохранение. Отдельная задача может добавить повторную отправку после потери сети.

Такой подход позволяет показывать работающие возможности постепенно. Разбиение только на «весь backend», «весь UI» и «все тесты» откладывает проверку пользовательского сценария до самого конца.

### Реализовывать по одной задаче

Для первого MVP предлагаю `$implement` на одну согласованную задачу за раз.

> $implement Реализуй GitHub Issue с указанным номером. Ограничь работу требованиями этой задачи.

Навык читает задачу, использует TDD там, где это уместно, запускает проверки, вызывает `code-review` и делает коммит в текущую ветку. Если важна отдельная ветка, укажи это в запросе до начала работы.

TDD здесь означает цикл «проверка нужного поведения падает → минимальная реализация проходит проверку». Навык требует заранее согласовать границы тестирования. Для Steady естественные кандидаты — интерфейс движка таймера и HTTP API сохранения результата. Конкретные границы выбираются при подготовке реализации.

Новая задача после этой должна опираться на её описание, спецификацию и код. Для продолжения в новом чате передавай ссылки на эти материалы.

## Какие действия происходят при вызове

| Навык | Что может изменить |
| --- | --- |
| `$setup-matt-pocock-skills` | Конфигурацию проекта; после согласования — метки GitHub |
| `$grill-with-docs` | Глоссарий и записи архитектурных решений по итогам обсуждения |
| `$to-spec` | Создать спецификацию в настроенном трекере |
| `$to-tickets` | Создать согласованные задачи и связи между ними |
| `$implement` | Изменить код, запустить проверки и ревью, сделать коммит |
| `$implement-spec` | Создать интеграционную ветку, раздать задачи агентам, объединить изменения и завершить работу по спецификации |
| `$code-review` | Запустить двух агентов для проверки diff и вернуть отчёты |
| `$retro` | Проанализировать сессию и предложить улучшения среды разработки |

`$implement-spec` — более автономный режим, чем `$implement`: он использует несколько агентов и worktree, учитывает зависимости задач и собирает общий результат. Для первой версии Steady проще управлять отдельными задачами через `$implement`, пока процесс не стал привычным.

Публикация спецификации или задач отличается от публикации приложения. Деплой, выпуск версии и слияние PR задаются отдельно соответствующим запросом и рабочим процессом.

## Как устроено ревью

`code-review` проверяет изменения относительно указанной точки Git и разделяет выводы на два направления:

- **Standards:** соблюдены ли правила проекта и нет ли проблем в устройстве кода.
- **Spec:** реализованы ли требования, нет ли пропущенного поведения или лишнего объёма.

Для прямого вызова укажи существующую ветку или коммит для сравнения. Например, после коммитов в рабочей ветке:

> $code-review Сравни изменения с main и проверь их по спецификации этой задачи.

Этот навык ориентирован на diff до `HEAD`; рабочие незакоммиченные изменения нужно явно оговаривать, поскольку его основной сценарий сравнивает коммиты.

Ревью даёт дополнительную проверку, но окончательную оценку поведения дают также выполненные тесты и ручная проверка приложения.

## Что означают метки задач

Стандартный словарь, предложенный при настройке:

| Метка | Значение |
| --- | --- |
| `needs-triage` | Задачу нужно разобрать |
| `needs-info` | Не хватает информации |
| `ready-for-agent` | Задача достаточно определена для реализации агентом |
| `ready-for-human` | Для реализации нужен человек |
| `wontfix` | Задачу выполнять не планируется |

`triage` полезен для сырых сообщений об ошибках и внешних запросов. Задачи, которые уже подготовил `to-tickets`, проходят прямо к реализации: повторный разбор обычно не нужен.

Метка сама по себе не запускает агента. Например, создание Issue с `ready-for-agent` делает задачу готовой к работе; выполнение запускается отдельным запросом или специально настроенной автоматизацией.

## Если забыл нужную команду

Начни с `$ask-matt` и опиши текущую ситуацию. Он выбирает маршрут по навыкам, а не пишет приложение вместо всех этапов сразу.

Полезные запросы:

- «`$ask-matt` У нас готова спецификация, хочу приступить к первой задаче».
- «`$ask-matt` Реализация завершена, нужно проверить соответствие требованиям».
- «Объясни проще: что произойдёт после вызова этого навыка?».
- «Сейчас только документация. Не создавай GitHub Issues».
